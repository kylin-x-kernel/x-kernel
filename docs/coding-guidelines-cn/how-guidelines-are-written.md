# 编写指南的方法

本指南集合中的内容体现了一套广泛认可的**理念**与**原则**，旨在指导编写高质量的软件。以下三本著作对指南的编写影响最为深远：
1. [_《可读代码的艺术》_](https://www.oreilly.com/library/view/the-art-of/9781449318482/)
2. [_《代码整洁之道》_](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)
3. [_《代码大全》_](https://stevemcconnell.com/books/)

这些指南源于**代码审查实践**——在审查过程中，我们识别代码坏味、观察反模式，并修复反复出现的缺陷。当指南的初版成型时，Asterinas 项目已经经历了数千次代码审查。我们将过往的审查意见进行了系统梳理。

并以此作为灵感来源与实证依据。

本页剩余部分将从理念转向实践。[理念](#philosophy)部分阐述了关于代码可理解性与可维护性的基本信念。[原则](#principles)部分将这些信念转化为指导日常决策的设计级规则。最后，[质量标准](#quality-criteria)部分定义了每条具体指南是如何编写并被纳入本指南集合的规范。

## 理念 {#philosophy}

### 最小化理解时间 {#minimize-time-to-understand}

代码的编写应以最小化他人完全理解它所需要的时间为准则。这是可读性的基本定理，也是本项目衡量代码质量的唯一最重要标准。"他人"包括未来的你自己。

代码被阅读的频率远高于被编写的频率。如果某种技巧能让代码更短，但更难以一目了然地理解，那么请选择清晰而非简洁。

### 管理复杂性是首要的技术要务 {#managing-complexity}

---

没有任何人能够将整个现代程序完整地保留在脑海中。软件构造中每一种技术的存在目的——分解、命名、封装、抽象——都是将复杂问题拆解为简单的片段，使你能安全地一次只专注于一件事情。

### 匠心与严谨 {#craftsmanship}

整洁的代码看起来就像是由在意它的人编写的。专业性意味着永远不要明知有乱麻却放任不管。想要保持快速前进的唯一方法，就是始终让代码保持整洁。

### 持续改进 {#continuous-improvement}

始终让代码比你发现它时更加整洁。

---
小而持续的改进——
重命名一个变量、提取一个函数、
消除重复——
能防止代码随时间而腐化。

## 原则 {#principles}

### 单一职责 {#single-responsibility}

每个模块、类型或函数
应当有且仅有一个变更的理由。
如果你在描述某个单元的功能时
必须使用"并且"、"或者"或"但是"这些词，
那它就承载了过多的职责。

---
### 不要重复自己 (DRY) {#dry}

每一份知识
都应当有单一、明确的表示。
重复会损害可读性与可维护性。
当相同模式出现三次或以上时，
应消除重复（例如，添加一个辅助函数）。

### 信息隐藏 {#information-hiding}

将设计决策隐藏在定义良好的接口背后。
模块的公共表面应当仅包含
其使用者所需的内容。
内部数据结构、辅助类型
和记录性字段应保持私有。
---

### 开放扩展，封闭修改 {#open-closed}

稳定的模块与 API 应
对扩展开放，
但对破坏性修改封闭。
优先通过现有接口
（trait、枚举与可插拔组件）
添加新行为，
而不是反复编辑已确立的调用路径。
不要预先引入扩展点；
应在出现具体扩展需求时再添加。

### 最小意外原则 {#least-surprise}

---

函数、类型和 API 的行为
应与它们的名称和签名所暗示的一致。
当显而易见的行为未被实现时，
读者会失去对代码库的信任，
并且必须退而阅读实现细节。

### 松耦合，强内聚 {#coupling-cohesion}

模块间的连接应当
是少量、可见且灵活的。
在模块内部，每一部分都应当
为一个单一、明确的目的而贡献。

### 一致性 {#consistency}

---
在整个代码库中，以相同的方式处理相似的事情。
一致性可以减少意外和认知负荷，
即使两种方式在客观上都不具优越性。
当已有约定存在时，请遵循它；
不要在没有令人信服的理由的情况下
引入相互竞争的约定。

### 测试作为信心的来源 {#test-as-specification}

测试存在的意义是让变更加安全。
一套全面的测试套件应给予开发者信心：
通过运行意味着系统正常工作，
失败运行则能精确定位问题所在。
每个测试都必须通过增强这种信心
来证明其存在的价值。
---

---
不发挥作用或反而起反作用的测试——
不稳定的测试、同义反复的断言、
与实现细节耦合的测试——
比根本没有测试还要糟糕。

### 拥抱 Rust 原生范式 {#rust-native}

Asterinas 的设计灵感来自 Linux，但并非 C 语言的移植品。
语言塑造了我们思考问题的方式：
C 代码依赖于约定和手动纪律
（返回值检查、配对初始化/清理、头文件契约），
而 Rust 则提供编译器强制保障的零成本抽象
（`?` 运算符、RAII、trait 约束）。

向 Linux 的设计思想学习，而非其惯用写法。

---
最终成果应读起来像地道的 Rust，  
而非用 Rust 语法编写的 C 代码。

## 质量标准 {#quality-criteria}

每条规范都应有一个**描述性的短名称**，使用连字符命名式（kebab-case）  
（例如：`explain-variables`、`lock-ordering`）。  
即使规范内容演变，短名称应保持**不变**，  
并在代码审查中引用规范时使用。

一条规范只有在满足以下所有四个质量标准时，  
才能被收录进本集合中：

1. **具体性** ——  
   表述为可操作的事项，并尽可能附上说明性示例。

2. **简洁性** ——  
   保持简短；我们不想让读者感到压力。
3. **有据可依** ——  
   有观点性或非显而易见的规范应包含“参见”行，附上支撑材料（文献、PR 审查、代码库示例）。
4. **相关性** ——  
   仅在满足以下条件之一时收录：有代码库示例、可预防历史缺陷、或与代码审查中观察到的反模式相匹配。

当存在 **“参见”行** 时，按以下顺序列出来源：  
文献；PR 审查；代码库示例。  
并非每条规范都需要三者齐全；  
对于强烈主观或非显而易见的规范，默认包含该行。

不要添加一条其唯一价值仅在于
已被自动化工具（如 [rustfmt](https://github.com/rust-lang/rustfmt) 和 [clippy](https://github.com/rust-lang/rust-clippy)）提供机械性强制执行的规范。
如果某个工具强制执行的约定在审查中频繁出现，
或需要特定于项目的理由说明，
则保留一条简短的解释性规范，并指向工具配置。
