# 性能审查规则

本阶段检查 PR 是否在可确认的执行路径上引入明显的延迟、吞吐、内存或资源使用回退。
开始分析前必须继续读取 `docs/ai/review/common.md`。

如需理解项目性能方法和证据边界，读取：

- `docs/ai/skills/code-guidelines/performance-and-resources.md`
- `docs/ai/skills/performance-analysis/SKILL.md`

## 核心原则

性能 finding 必须同时具备：

1. 成本：新增了什么分配、拷贝、遍历、锁竞争或昂贵操作；
2. 频率：它处于什么调用频率或循环层级；
3. 规模：输入、集合、CPU 数或对象数量如何放大成本；
4. 后果：影响延迟、吞吐、内存峰值还是资源耗尽；
5. 修复方向：可以移出热路径、复用、批处理或换用更合适的数据结构。

只看到 `clone()`、循环或锁不足以形成 finding。
如果无法证明路径频率和规模，应不报告或继续搜索调用方。

## 强制工作流

1. 使用 `get_annotated_diff` 获取变更并标记潜在成本点。
2. 用 `read_file` 阅读相关完整文件，确认循环、锁和资源的外层上下文。
3. 用 `search_content` 搜索调用方，判断它是初始化、控制面还是 fast path。
4. 确认数据规模来自哪里，是否存在明确上界。
5. 搜索项目已有缓存、索引、批处理或零拷贝抽象，避免建议重复实现。
6. 对复杂度变化写出变更前后的数量级或每次调用新增成本。
7. 只报告对实际工作负载有意义的问题，不输出无证据的微优化。

## 重点检查项

### 1. 分配与释放

检查：

- 循环、syscall、IRQ、调度、页错误或网络收发路径中的 heap 分配；
- 每次调用重新创建 `Vec`、`String`、`Box`、map 或临时缓冲区；
- 已知容量却反复扩容，未使用 `with_capacity` 或复用容器；
- 小对象被不必要地装箱或转为动态分发；
- 对象生命周期被扩大，导致内存峰值或资源占用时间增长；
- 错误路径和缓存淘汰路径没有及时释放大对象。

初始化阶段的一次性小分配通常不是 finding，
除非它发生在受限的 early boot 环境或可能导致启动失败。

### 2. 拷贝、克隆与数据移动

检查：

- 大结构按值传递或在多层调用中重复 clone；
- packet、page、I/O buffer 和用户数据的重复中间拷贝；
- `to_string()`、`to_vec()`、序列化和格式化结果只被短暂读取；
- `Arc` clone 出现在内层循环或高频查找中；
- 可以借用 slice、迭代器或已有缓冲区却创建完整副本。

必须结合类型大小、数据长度和频率判断。
不要把 cheap handle clone 与深拷贝混为一谈。

### 3. 算法复杂度与数据结构

重点关注：

- 热路径从 O(1) / O(log n) 退化为 O(n)；
- 在集合遍历内部再次线性搜索形成 O(n²)；
- 每次查询都排序、收集或完整扫描全局表；
- CPU 数、任务数、VMA 数、fd 数、页数或设备数会放大操作；
- 本应使用索引、区间结构、bitmap 或队列，却反复扫描。

评论需要说明 `n` 代表什么，以及路径为何会处理较大的 `n`。

### 4. 锁与并发扩展性

检查：

- 扩大锁临界区，尤其包含分配、I/O、日志、遍历或回调；
- 把 per-CPU / per-object 状态改为全局锁保护；
- 读多写少路径改用独占锁；
- 在高频路径加入 contended atomic 或全局计数；
- 批量操作拆成每项一次锁获取；
- cache line 上新增高频跨 CPU 写入导致伪共享。

高 acquisition 次数不等于瓶颈。
必须结合可并发调用路径、锁持有工作量或已有性能证据。

### 5. 冗余工作

检查：

- 循环中重复计算不变量；
- 同一数据被重复解析、校验、hash 或格式化；
- 已缓存或已由上层验证的信息被重新构造；
- 即使结果不会被使用也执行完整操作；
- 日志参数在日志级别关闭时仍完成昂贵计算；
- 无变化时仍刷新 TLB/cache、提交 I/O 或广播跨 CPU 操作。

### 6. I/O、内存和架构敏感路径

对以下场景提高审查深度：

- page fault、页表修改、TLB shootdown 和 cache maintenance；
- block / filesystem I/O 合并与拆分；
- network packet 分配、复制和 checksum；
- scheduler enqueue/dequeue、wakeup 和 timer；
- IRQ handler、softirq 和 workerqueue；
- MMIO、barrier 和跨 CPU IPI。

这些路径中“减少一次操作”也可能重要，
但必须先证明新增操作实际位于每页、每包、每任务或每中断路径。

## 不应报告的情况

- 冷路径上一次性的清晰实现，仅理论上能少一次小分配；
- 编译器能够可靠消除的局部临时值；
- 没有数据规模和调用频率证据的 Big-O 猜测；
- 用更复杂缓存换取未经测量的优化；
- 建议改用 unsafe 只为避免小拷贝；
- 以可读性、正确性或边界校验为代价的微优化。

## 输出要求

遵循 `common.md` 的 finding JSON 格式。
正文应明确说明成本、频率/规模和后果。
如果结论需要 benchmark 才能成立，应把它表述为需要验证的观察，
而不是直接作为确定 finding 输出。
没有高置信度性能问题时输出 `未发现问题`。
