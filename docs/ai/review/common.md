# 自动代码审查公共规则

本文件定义 POSIX、Bug、Performance、Logic 和 Guidelines 阶段共同遵守的
证据标准、分析边界和输出协议。
各阶段在阅读自己的规则文件后，必须继续完整阅读本文件。

Description 阶段不使用 finding JSON，按 `description.md` 的独立契约执行。

## 审查目标

自动审查的目标是发现能够明确定位、能够解释影响、值得 PR 作者立即处理的问题。
审查不是对 diff 做摘要，也不是罗列所有可能的改进方向。

一个合格 finding 至少要回答：

1. 哪个具体变更引入了问题；
2. 在什么输入、状态或执行路径下会触发；
3. 会产生什么可观察后果；
4. 为什么当前代码或已有保护不能阻止它；
5. 最相关的可评论 diff 行在哪里。

如果无法回答其中关键部分，应继续查证或放弃报告。

## 强制工作流

### 1. 获取带行号 diff

首先调用 `get_annotated_diff` 获取变更。
后续评论的 `line` 和 `side` 必须来自这个工具给出的 `L` / `D` 标注。
API 返回的普通 patch、`read_file` 行号或搜索结果行号都不能替代 annotated diff 行号。

### 2. 建立变更清单

按文件和变更性质整理范围：

- 新增、删除或修改了哪些类型、函数、trait、配置和文档；
- 是否改变公共 API、模块边界或 crate 依赖；
- 是否涉及 syscall、用户内存、unsafe、并发、资源生命周期或热路径；
- 是否存在生成文件、测试文件或仅机械性修改。

先分类再选择检查深度，避免对所有文件机械套用同一清单。

### 3. 阅读完整上下文

对可能形成 finding 的变更，必须用 `read_file` 阅读相关完整文件，至少确认：

- 函数签名、类型定义和 trait 契约；
- 调用前置条件和返回值处理；
- 锁、引用、资源和对象生命周期；
- 相邻注释、rustdoc、测试和条件编译；
- 修改点是否处于 fast path、异常路径、初始化或清理路径。

文件超过工具单次返回上限时应分页读取，不能把截断内容当作完整上下文。

### 4. 搜索影响范围

使用 `search_content`、`search_files` 或只读 `git` 命令查找：

- 修改函数和类型的调用方；
- 同一 trait 的其他实现；
- 同架构和其他架构的对应实现；
- 已有 helper、封装、测试和错误处理惯例；
- 配置项、feature、Kconfig 和 Cargo 依赖的使用点。

只有确认调用方式和代码库现状后，才能声称“调用方会失败”或“已有实现可复用”。

### 5. 验证并定位

输出前重新核对触发条件、后果和行号。
优先选择导致问题的新增行，而不是只承载现象的下游行。
如果问题依赖未证明的假设，应在本阶段不报告。

## 证据等级

以下情况通常具备足够证据：

- 从新增代码可以构造明确的失败路径；
- 调用方或 trait 契约证明参数可能取到问题值；
- Linux / POSIX 文档明确规定了不同语义；
- 项目已有封装或同类实现明确展示了必须维护的不变量；
- 算法复杂度与已确认的热路径或数据规模共同构成实际风险；
- 删除或遗漏的清理操作能沿所有权路径证明资源不会释放。

以下情况通常不应报告：

- 只凭函数名、单段 diff 或个人风格偏好推断；
- “可能更快”“也许会 panic”“建议加测试”但没有触发条件；
- 现有代码中的历史问题，且本 PR 没有修改或扩大它；
- 编译器、类型系统或现有校验已经排除的问题；
- 需要跨多项未知前提才可能发生的理论风险；
- 单纯格式问题，能够由 rustfmt 自动处理且不影响语义。

## Review 范围

以 PR 新增和修改代码为主。
上下文代码只用于证明问题，不应借机评论无关历史债务。

如果 PR 修改了一个原本有缺陷的区域：

- 新代码直接引入、恢复或扩大缺陷，可以报告；
- 缺陷完全存在于未修改代码，不能挂靠在附近新行上报告；
- 新 API 使原有不安全行为暴露给更多调用方，可以报告新增影响。

## 输出格式

每个 finding 输出一个 JSON 对象，多个对象之间用单独一行 `---` 分隔：

```json
{"file":"relative/path.rs","line":42,"side":"new","body":"中文问题描述"}
```

字段规则：

- `file`：PR 仓库内的相对路径，必须与 diff 路径一致。
- `line`：最相关的一条可评论行号，只能填整数。
- `side`：新增行或上下文行用 `"new"`，删除行用 `"old"`。
- `body`：使用中文，语气友好、直接、可执行，支持 Markdown。

不要输出 `start_line`、`start_side`、严重级别或协议外字段。
不要使用代码围栏包裹整个 JSON 对象。
如果没有发现问题，最终只输出：

```text
未发现问题
```

## 行号选择

- 新增行选择 annotated diff 的 `L<行号>`，使用 `side: "new"`。
- 删除行选择 `D<行号>`，使用 `side: "old"`。
- 同时有 `L` 和 `D` 的上下文行，通常选择 `L` 和 `new`。
- 多行共同构成问题时，选择最能体现根因的一行，不扩展评论范围。
- 如果最相关代码不在 diff 可评论范围内，不要把评论强行挂到附近无关行。

## 评论正文

推荐使用“问题 — 触发条件 — 后果 — 建议”的紧凑结构：

```text
这里在持有 `task_table` 写锁时调用了可能阻塞的 `wait()`。
当被等待任务退出路径也需要获取该锁时，两条路径会互相等待并造成死锁。
请在进入等待前释放锁，或把所需状态复制到锁作用域外。
```

正文不要：

- 只写“这里有问题”或粘贴规则原文；
- 使用“肯定会”“一定”描述尚未证明的行为；
- 长篇复述整个函数；
- 同一评论混合多个独立问题；
- 要求作者顺手重构与本 finding 无关的代码。

## Suggestion block

当修复是可靠的单行替换时，必须在 `body` 中使用 ````suggestion` 块。
典型场景包括：

- 重命名变量、参数、函数、trait 或模块；
- 收窄 `pub` 可见性；
- 将成员 crate 依赖改为 `workspace = true`；
- 去掉已使用参数的 `_` 前缀；
- 把 `let _ = fallible_call()` 改为明确传播或处理；
- 同步一行明显过期的注释或 rustdoc。

要求：

1. suggestion 内容必须能完整替换评论所在的单行；
2. 必须是语法完整、与上下文匹配的代码；
3. 修复涉及多行、签名和所有调用方时，不使用 suggestion；
4. 不能只给表达式碎片或伪代码；
5. suggestion 中的代码注释必须使用英文；
6. 无法确信修复正确时，只说明约束，不提供 suggestion。

## 最终自检

输出每条 finding 前确认：

- [ ] 已阅读阶段规则和本公共规则；
- [ ] 已取得 annotated diff；
- [ ] 已阅读问题所在文件的完整上下文；
- [ ] 已搜索必要的调用方、实现或参考代码；
- [ ] 触发条件和用户可见后果明确；
- [ ] 问题由当前 PR 引入或扩大；
- [ ] 行号和 side 可评论且准确；
- [ ] 正文使用中文且只讨论一个问题；
- [ ] suggestion（如有）可以直接替换目标行。
