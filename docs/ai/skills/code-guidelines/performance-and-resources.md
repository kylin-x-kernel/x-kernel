# Performance And Resources

Use this file when the change touches hot paths,
allocation behavior, copying, ownership, or cleanup.

## Performance

- avoid O(n) algorithms on hot paths unless justified;
- avoid casual atomics in frequently executed code;
- minimize unnecessary copies and allocations;
- do not optimize prematurely without evidence,
  but do not ignore obvious structural costs either;
- make semantic costs visible in naming and API shape.
- when claiming a performance improvement,
  be prepared to justify it with evidence.

## Data Structure Selection

- choose containers by access pattern, not by habit;
  `Vec` is a good default only for append, tail pop, indexed access,
  and iteration-dominated usage;
- do not use `Vec` as the default for queues, wait lists, or pending
  lists that need frequent removal from arbitrary positions or
  ownership-driven unlinking; `Vec::remove`/`Vec::insert` shift the
  tail on every call (O(n)), and per-scan removal loops degrade to
  O(n^2);
- for linked-list needs use the project-standard intrusive list
  `linked_list_r4l` (workspace dependency): `List` plus `Links`
  embedded in the element or generated by `def_node!`, as done by
  `ksched` ready queues and `kprocess`; intrusive linkage gives O(1)
  unlink at a known element, stable element addresses while queued, and
  no per-node allocation or relocation;
- fall back to `alloc::collections::LinkedList` only when elements
  cannot own their linkage (for example the list must outlive or be
  decoupled from element ownership);
- on IRQ-safe or otherwise allocation-free paths, prefer fixed-capacity
  storage (bounded rings or preallocated slots) over any growable
  container; growth implies allocation, element copying, and contiguous
  memory pressure that enqueue paths must not pay;
- remember `Vec` growth needs one larger contiguous allocation and moves
  every element, invalidating element addresses; node-based containers
  never relocate live elements;
- when several call sites need the same bounded access pattern, provide
  one shared audited container (for example a fixed-capacity entry ring)
  instead of ad hoc `Vec` bookkeeping per caller;
- weigh linked-list costs honestly before choosing them: pointer chasing
  during iteration and stricter lock discipline; intrusive `Links` also
  restrict an element to one list per `Links` field at a time, so make
  multi-list membership explicit in the element design.

## Resource Management

- use RAII and ownership-based cleanup by default;
- avoid lifetime splits that make cleanup obligations ambiguous;
- keep acquire/release symmetry easy to audit;
- when a resource must outlive a scope boundary,
  make that ownership transfer explicit.

## When Reviewing

Check specifically for:

- linear scans in interrupt, scheduler, packet, or page-fault adjacent paths;
- hidden heap allocation in frequently repeated operations;
- redundant copies of large buffers or descriptors;
- `Vec` used as a queue or pending list that sees middle removal,
  needs stable element addresses, or is touched from IRQ-safe paths;
- linked-list needs served by ad hoc structures or non-intrusive lists
  instead of the project-standard `linked_list_r4l`;
- `Vec::remove`/`Vec::insert` inside loops, or `Vec` growth on hot paths;
- large elements stored by value in growable `Vec`s where
  reallocation copies dominate;
- cleanup paths that depend on manual caller discipline
  when ownership could encode the rule directly.
