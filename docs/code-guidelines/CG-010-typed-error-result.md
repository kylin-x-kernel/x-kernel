# CG-010-typed-error-result: Use typed `Result` errors

- **Rule**: Function signatures must not use `()`, `&str`, or `String` as a `Result` error type.
- **Scope**: Public and private function and method signatures, including tests, trait methods, and foreign function declarations, in code compiled by the selected configuration. Only the core/std `Result` type is checked; same-named user types are not. The lint checks resolved error types, including aliases.
- **Why**: A typed error communicates the failure modes at the layer boundary and can carry structured context.
- **How to check**:
  1. Inspect each function's returned `Result<T, E>` type.
  2. Replace the listed untyped error types with an error enum or an existing layer-appropriate error type.
- **Exceptions**: No blanket exception. Code generated by a third-party macro is exempt only when the macro fixes the generated `Result` error type and the project cannot select another type. For `enum_dispatch`, the exemption applies only to generated methods in impls whose resolved trait is core/std `TryFrom` or `TryInto` and whose defining expansion ancestry includes `enum_dispatch::enum_dispatch`. Handwritten methods passed through an annotated trait, handwritten conversion impls, and unrelated generated items remain checked. A genuinely external API constraint requires review and an allow reason naming that constraint.
- **Counter-example**:

```rust,ignore
fn parse(input: &str) -> Result<Value, String>
```

The signature hides the parser's failure cases in a string.
- **Example**:

```rust,ignore
fn parse(input: &str) -> Result<Value, ParseError>
```
- **Run**: `make dylint` scans the configured kernel; `make dylint_test` runs UI tests.
