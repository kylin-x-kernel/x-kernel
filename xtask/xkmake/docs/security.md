# xkmake — Security and Reliability Analysis

## Trust Model

`xkmake` is a host-side development tool. It trusts the repository source code, but treats the CLI, environment variables,
`.config`, file paths, and extra QEMU arguments as local inputs that need validation.

## External Boundaries / Attack Surface

- Invokes Cargo build/rustdoc, cross GCC/binutils, `rust-objcopy`, FAT/mtools,
  QEMU, `debugfs`, cargo-shear, licensure, and the Rust LLVM coverage tools;
- Reads the user-specified configuration, the `linker.lds.S` template at the repository root, application crates,
  and disk images;
- Writes the Cargo target directory, the generated configuration, and bundles, and refreshes the `xkernel_<platform>.*` compatibility copies in the repository
  root from a valid bundle;
- Passes the arguments after `--` to QEMU.
- Passes the arguments after `xkmake doc --` to `cargo doc` one by one.

DWARF section embedding (the former `dwarf_embed` tool) is now done inside the xkmake process
and is no longer invoked as an external subprocess. Its ELF rewriting logic propagates errors as `Result` throughout and performs bounds
checking, but if this logic fails it directly affects the `xkmake build` process instead of being isolated. This path
is enabled only when KFEAT_DWARF=y; the boot image of a default build carries no DWARF data.

The compact symbol table (KFEAT_SYMTAB) is generated by xkmake by extracting function symbols from the kernel ELF: only
functions in `SHF_EXECINSTR` sections are collected, sorted and deduplicated, and written to `$TARGET_DIR/kbuild/
ksymtab.bin`, which `util/backtrace` copies via build.rs and embeds into `.rodata` with `include_bytes!`.
The generation logic runs entirely in-process with length/type validation; symbol names
come from the ELF strtab and are treated as build artifacts rather than external input.

Image metadata finalization is likewise done in-process. Before writing, it must verify that the note header, owner,
descriptor size, file range, and section all lie within both the file range and the virtual address
range of a `PT_LOAD` segment. XKMake does not add program segments after linking; it only modifies bytes reserved by the linker.

All external commands are constructed through `std::process::Command`, without concatenating shell command strings.
QEMU vsock capability is probed through a read-only `-device help` subprocess; a probe failure only disables
vsock and emits a warning, and does not prevent a VM without vsock from starting. Availability probing for ports and CIDs
only binds a temporary socket within this process, or issues a
`VHOST_VSOCK_SET_GUEST_CID` request to `/dev/vhost-vsock`; it does not access any external service. CID probing temporarily occupies
a candidate CID, and closing the probe fd immediately releases that CID, so no kernel resources are held for long;
`--dry-run` performs no probing at all.

LinuxBoot header and image assembly are done in-process; ELF symbols, lengths, offsets, and integer
conversions are all validated before files are written. The UEFI image capacity is computed from the input file lengths, inputs exceeding the FAT32
single-file size limit are rejected, and capacity arithmetic is checked for overflow; only temporary bundle paths are written. The OVMF firmware is treated as an
external trusted input chosen by the user; the writable VARS uses a copy of the template, and XKMake does not modify the original template.

The documentation flow obtains features only from the resolved configuration snapshot. Extra Cargo arguments are not
evaluated by a shell, but they can change Cargo's output location or build behavior, and are an explicit advanced-user capability.

The dependency check only runs a pinned version of `cargo-shear`, passing controlled
workspace paths as structured arguments. `--locked` is passed only for workspaces whose `Cargo.lock` is tracked by Git (the kernel root
workspace), to prevent the analysis from rewriting the lockfile; the lockfiles of the other tool
workspaces are gitignored and generated by cargo on demand. `--fix` is a repository write operation explicitly
chosen by the user, and it modifies the Cargo manifests of dependencies judged to be unused.

The header check obtains tracked and non-ignored Rust files through Git, and passes only the relative
paths that still exist, in batches, to the pinned version of licensure. Check mode is read-only; `--fix` is an explicit write operation
that updates the beginning of source files according to the repository-root `.licensure.yml`, and forces a re-check after writing.

The lint inheritance check is read-only: it calls `cargo metadata --no-deps` and parses member manifests,
without running build scripts or modifying files.

The coverage flow reads the user-specified disk image only when the unittest QEMU exits normally and this round's newly created `qemu.log` also confirms
that the tests passed and that the coverage write/fsync/filesystem sync succeeded.
Even if an old profile can be decoded by LLVM, it cannot substitute for the guest's persistence marker of this round.
The marker is the completion protocol of the trusted test kernel, not a proof of authenticity against a malicious guest.
The guest and host paths in a `debugfs` request are escaped according to its command lexical rules; report commands all run with
structured arguments, interpret the profile with the complete `kernel.debug.elf` of the same bundle,
and the LCOV to Cobertura conversion is done inside the XKMake process.

`dylint --facts-out <dir>` deletes and rewrites `<dir>/crates`,
`manifest.json` and `status.json`; the directory is given explicitly by the
caller (a relative path is resolved against the repository root). The facts
files are written by the lint library in the scan process; XKMake only reads
the files next to the workspace units listed in Cargo's JSON messages and
validates the header's schema and stem and the final totals, without
executing any of their content. The exporter is repository code, so a pull
request can change it and thereby its own facts; the manifest records the
exporter source digest (`exporter.source_sha256`), and consumers decide to
trust only the digest of a trusted tree (the target branch). Facts are a
review aid only, never a gate.

`--facts-deps` makes Cargo invoke XKMake itself as `RUSTC_WRAPPER`. The
wrapper is active only when `XKMAKE_FACTS_WRAPPER_TARGET` is set and the
first argument is a compiler (`rustc`, Cargo's `RUSTC` or the Dylint
driver), so an `xkmake` started inside the scan, which inherits the
variable, keeps its normal command line; the wrapper uses
`exec` with structured arguments, never a shell, to run the rustc given by
Cargo or Dylint's `RUSTC_WORKSPACE_WRAPPER`. For dependencies it only
appends `--force-warn facts_export` and leaves the other arguments unchanged,
so the dependencies' other lints stay silenced by `--cap-lints allow`.

`symbolize` only invokes `llvm-addr2line`/`addr2line` (which can be specified explicitly with `--tool`),
passing the ELF and addresses as structured arguments; log content is only read to extract addresses, and the tool does not execute
anything in the log. When `kernel.debug.elf` has not been built, the tool reports an explicit error and does not fall back to
guessing an artifact.

## Security Model: backtrace and Debug Data

- The `kernel.bin`/boot image of a default build (KFEAT_DWARF=n) contains no `.debug_*`
  data; DWARF exists only in `kernel.debug.elf` (a host artifact that can be distributed separately);
- When KFEAT_DWARF=y, the image carries full DWARF, and runtime symbolization depends on gimli/addr2line
  and dynamic memory allocation; it is intended only for environments without a host toolchain;
- KFEAT_SYMTAB keeps function names and addresses in the image (on the order of MB) and is off by default;
  when enabled, the exposed surface is function symbol names, without line numbers or source paths;
- In any mode, the kernel can always output a raw-address backtrace, and host-side restoration does not depend on
  any runtime debug data.
- The boot ELF uses `rust-objcopy --strip-all` to remove non-loaded host analysis information;
  `PT_LOAD` data, the BSS layout, the per-CPU template and runtime profile data are unchanged.
  On x86 only the `rust_entry` and `boot_stack_top` static symbols required by the boot contract are additionally kept.
  Host DWARF and coverage maps are kept only in the complete analysis ELF, so that they are not copied with the ELF boot payload,
  kept, and made to occupy early available RAM.

## unsafe Code Inventory

This crate contains no `unsafe` code.

## Reliability Invariants

- After `BuildContext` is constructed, all stages use the same architecture, platform, target, and
  profile.
- The linker script is rendered only from the `linker.lds.S` template embedded from the repository root and the resolved
  configuration snapshot;
  when the target content is unchanged the file is not rewritten, keeping mtime stable and preserving Cargo incremental compilation semantics.
- ELF, BIN, LinuxBoot, UEFI, and the manifest are all first written to temporary paths in the same directory.
- Before promoting artifacts, the old manifest is removed first, and the new
  manifest is promoted last, after all artifacts have been promoted successfully; a failed build does not leave behind a new valid manifest.
- An ordinary build treats a bundle atomically published by XKMake in the same workspace as a trusted local
  cache; reuse requires that the stable build provenance, artifact names/sizes/mtimes, the Cargo ELF, and the x86 boot
  input times all match. `--no-build` is the boundary for consuming existing artifacts; in addition to the checks above, it uses the
  build information and Build ID saved in the manifest to recompute the complete loadable-image hash.
  The automatic current time does not participate in cache decisions; an explicit `KBUILD_BUILD_TIME` or
  `SOURCE_DATE_EPOCH` override value does participate in matching.
- The Build ID is generated after build-info and DWARF finalization complete; the hash covers all
  `PT_LOAD` contents and treats its own descriptor as zero, to avoid a circular definition.
- Root-directory compatibility artifacts are copied only from a committed, valid bundle, first written to a temporary path in the same directory
  and then renamed to the final name; a copy failure makes build return an error, keeps the old compatibility artifacts,
  and does not change the validity of the bundle manifest. The copy is skipped when the size and mtime of the target copy already cover the source
  artifact; otherwise the standard library prefers the platform clone/reflink capability, and falls
  back to an ordinary copy when it is unsupported.
- A non-zero exit of an external command immediately terminates the current flow, and old artifacts are not consumed further.
- Facts packing writes the crate files and the manifest first and
  `status.json` last; the manifest and the status are both committed by
  renaming a temporary file in the same directory. The status becomes
  `ready`/`partial` only after packing completes, and an interrupted run
  stays at `running`. A run removes the previous artifact before it reads
  the configuration, so a run that fails early never leaves an earlier
  `ready` status in place.

## Known Limitations

- Extra QEMU arguments can change the VM security boundary; this is an explicit advanced-user capability.
- Flows that require privilege escalation, such as tap, bridge, and VFIO, are not yet implemented, and sudo is currently not invoked automatically.
- The current bundle hash does not cover the tool version; the manifest format version is used to reject future
  incompatible formats, but the forced-rebuild policy after a tool upgrade still needs to be improved.
- The guest IP/gateway currently enter the compile environment and may leak into inspectable kernel binaries.

## Audit Checklist

- When a new external program is added, are structured arguments still used?
- Does a new bundle field enter the compatibility check or the format version?
- Does new ELF post-processing still write only the linker-reserved range and verify `PT_LOAD` containment?
- Is a new path restricted to the expected output directory, or explicitly specified by the user?
- Can a failure path leave behind a seemingly valid manifest?
- Does a new run option complete combination validation before QEMU is started?
